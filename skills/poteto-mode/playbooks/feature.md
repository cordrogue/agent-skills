### Feature

**You own the design. Plan, review, verify.** Delegate implementation. Stay in the lead.

1. `how` over the affected subsystem. When the feature replaces or deletes existing code, give one explorer the old behavior as its angle. It lists what each old reader, writer and screen does for the user, and each scenario the deleted tests check. The design maps each to a new equivalent, a ported test, or a default the operator sees. K7's design listed only the code to delete, and audits found seven lost behaviors.
2. `architect` for parallel design exploration. When the feature changes how a screen is organized, grouped, labeled, or gives feedback, or deletes a screen or a section of one, read `.agents/skills/design-foundations/SKILL.md` first.
3. Write the throughput checkpoint as four todo items. A dimension that genuinely does not apply (single file, no fan-out) keeps its item with `n/a: <reason>` rather than being dropped:
   - **Blocking first steps.** Gates run before fan-out.
   - **Independent workstreams.** Disjoint files, services, or layers parallelize when no writer turns another writer's tests red. A writer that changes seed data, a fixture or a snapshot owns every test that reads it, or the writers serialize. Shared writes serialize.
   - **Shared mutable state.** Default to splitting the target (the **separate-before-serializing-shared-state** principle skill). Serialize only for real invariants.
   - **Smallest safe decomposition.** If one worker is best, name why.
   - **Red move.** When deleting old code leaves each writer's branch red alone, first delete it in a scratch worktree, run `npm run typecheck`, and give each erroring file a writer or the integrator. Each brief names the integrator and the tests expected to fail, with each one's owner. Writers commit `WIP:` subjects with final bodies, pin dependencies to a SHA, and never read or edit another writer's worktree. The integrator merges in a `<unit>-int` worktree, rebuilds the final ordered commits, and ends on an empty `git diff` against the green merge.
4. Delegate code-writing to a subagent using the `feature, refactoring` model in `../references/models.md` with a specific scope (file paths, named data shape and its organizing structure per **principle-model-the-domain**, a state machine over scattered booleans, a table/registry over branching, a typed model over repeated shape assumptions, chosen before the delegate writes logic, and success criteria stated as the invariant the user sees, such as "exactly one sidebar item is marked", with every state it must hold in). When the implementation admits multiple valid shapes (error handling, abstraction layer, test structure, or what a shared read returns, such as its sort key, cursor or fields), delegate via the **arena** skill instead so the runners surface the alternatives and the cross-judge guards the pick. A brief that changes a shared read lists every consumer of it, agent and MCP tools included, and how each one joins or refreshes results. A brief deletes nothing that step 1's map leaves unmapped. Mandatory: no skip-with-reason escape, and Laziness Protocol does not override it (the gain is review separation, not lines saved). A subagent forbidden to spawn satisfies this by owning the diff directly with the same review separation. No "standing by" reply that waits on a nested agent. Comments per **Comments**. Surgical edits, re-ground against the source for upstream-derived files. A brief that moves an existing thing onto a template takes only the shape from the template and every value (limits, accent, options, labels, icon) from the old definition, with a citation. Keep the old code's state location, reload behavior, and the process doing the work. These are behavior, not template shape. Batch writer-reported changes for the operator with today's behavior as the default. Check each value a writer reports as 'same as the template' against the old definition before you accept it. Port shared-primitive improvements to all consumers and verify each. Commit liberally. Before each handoff to a writer or a reviewer, the design states only its final meaning. Accepted review findings rewrite the affected sections in place. Superseded choices go only to the decision log.
5. Verify on the matching surface. The live check tries the edge case that the design's claim depends on. "Inconclusive" or wrong-surface is not a pass. Flag it.
6. Rebase into small, ordered commits. Stack follow-ups.
   Use the **sequence-verifiable-units** principle skill, building, verifying, and committing each small unit before the next.
7. If the design is contested, `interrogate` before shipping. Apply step 4's design handoff rule before review.
8. Run **Landing on main**.

Code-coupled work (one feature, one migration) goes to a single owner with the checkpoint inline. That owner fans out internally after the blocking phase. Parent-level fan-out is for slices that produce independent artifacts (audits, cross-subsystem investigations, competing experiments). Rewrite the checkpoint at phase boundaries. Spawn a fresh owner rather than chaining interrupts.

**Reply:** what you built, what you chose and why, the throughput checkpoint, open decisions. Tables for design alternatives.
